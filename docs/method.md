# 手法: リバースエンジニアリングから照合まで

SKILL.md が「何を実行するか」の手順書であるのに対し、この文書は
「**どう判断するか**」を掘り下げる。実コードから形式モデルを逆抽出する際の
勘所と、各フェーズの考え方を記す。

## 全体の流れ

```
1. 調査      コードを読み、概念・状態・遷移・不変条件・関係を見立てる
2. 構造      CUE でスキーマ・語彙・関係を書く        (cue vet)
3. 振る舞い  Quint で状態・遷移・不変条件を書く      (quint typecheck/test/verify)
4. 投影      projection.cue で状態差分の意味づけを書く
5. 整合      check-consistency で CUE↔Quint の語彙整合を検査
6. 照合      explain/project でビューを出し、現実と突き合わせる
   └─ 食い違いを見つけたら 2〜4 に戻って直す(ループ)
```

## 1. 調査: 何を探すか

コードを読んで、次を**書き出しながら**見立てる。頭の中だけでやらない。

| 探すもの | 問い | 例(todo-cli) |
|---|---|---|
| 概念/エンティティ | 名詞は何か。属性は何か | Task(id, title, status, createdAt, completedAt) |
| 状態 | エンティティが取りうる離散状態は何か | backlog / active / done |
| 遷移 | 状態を変える操作は何か。前提条件(ガード)は何か | start: backlog→active |
| 不変条件 | 常に成り立つべきことは何か | idは再利用しない; completedAtはdoneのみ |
| 関係 | 概念同士はどう繋がるか | (状態機械なら状態間の遷移自体が関係) |

### 観測事実と意図の区別

- **観測事実**: コードが現にやっていること。`start` は `backlog` 以外を拒否する、等。
  これはモデルに**そのまま**書く。
- **意図の推測**: なぜそうしているか。コメントや命名から推む。これは**散文**として
  残し、モデルには含めない(含めると願望が混ざる)。

モデルに書くのは観測事実のみ。意図を形式化すると「コードに無い振る舞い」を
モデルが主張し始め、照合の基準が壊れる。

## 2. 構造(CUE): どこまで書くか

- **スキーマ**: コードが読込時に行っている検証を写し取る。`persistence` 層が
  「重複IDを拒否」「doneならcompletedAt必須」を検査しているなら、それもスキーマに書く。
  コードの検証ロジックは「構造の不変条件」の宝庫である。
- **語彙**: 各概念に `id`(安定識別子)・`preferredName`(表示名)・`definition`(定義)。
  表示名とidentityを分離するのが肝。名前が変わってもidは変わらない。
- **関係**: 概念間の繋がりを `relations` で明示。自然言語に埋めない。

`cue vet -c` で構造を検証する。ここで「語彙の一意性」や「参照整合性」を
構造的に強制できるのがCUEの強みである。

## 3. 振る舞い(Quint): どこまで書くか

- **状態変数**: システムの本質的な状態だけを `var` で。細部(個々のタスクのtitle等)は
  抽象化してよい。振る舞いモデルの関心は「何がどう変わりうるか」。
- **遷移**: 1操作=1アクション。ガード(前提条件)を明示する。ガードこそが
  「許される振る舞い」の定義である。
- **不変条件**: 「常に成り立つこと」を `val` で。例:「idは再利用されない」
  「勝利と敗北は排他」。不変条件はモデルの主張であり、`quint verify` で全経路を検証できる。
- **シナリオテスト**: `run ...Test` で代表的な筋を書く。宣言(期待する振る舞い)になる。

### 不変条件が空虚でないか確認する

不変条件を意図的に外して `quint verify` にかけ、違反トレースが出るか確かめると、
その不変条件が**実際に制約として機能している**ことを証明できる(ミューテーションテスト)。
常に自明に真の不変条件は書く価値が薄い。

## 4. 投影(projection.cue): 意味づけの宣言

「状態差分が何を意味するか」を宣言する。ここが**システム固有の解釈**の置き場所。

- ナラティブ(参加者間の相互作用)なら `message`(シーケンス図)。
- 状態機械(レコードの状態変化)なら `transition`(状態遷移図)。

差分述語(`setGains` / `move` / `intDecreases` / `boolBecomes` 等)のANDで
イベントを検出し、`bind` で捕まえた値を `from`/`to` で `$<bind>` として参照する。
詳しくは `conventions.md` と `examples/*/spec/projection.cue`。

## 5. 整合: CUE↔Quint の語彙を揃える

`check-consistency` は次を検査する:
- Quintの文字列リテラルがCUEの既知idか(未知idは失敗)
- Quintに日本語/生リテラルが漏れていないか
- `constants.qnt` がCUEと一致しているか(鮮度)

これにより「QuintはCUEの語彙を参照する」という約束が機械的に保たれる。

## 6. 照合: メンタルモデルを築く

`explain` で全部入り解説書を出し、人間と現実(実コードの実際の挙動)に突き合わせる。

- **学習モード**: 初めてのシステムで `explain` を叩き、用語→構造→振る舞いの順に
  メンタルモデルを築く。
- **分析モード**: 特定のシナリオ(`--test`)やcounterexample(`--trace`)を投影し、
  「なぜこうなるか」を調べる。

食い違いは発見である。モデルを直して再投影し、収束させる。

## 判断に迷ったら

| 迷い | 指針 |
|---|---|
| これ形式化するべき? | 機械検査して価値があるか。なければ散文で |
| どこまで詳細に? | 振る舞いの本質だけ。細部は抽象化 |
| どのビュー? | システムの構造に合うもの。ナラティブ→シーケンス、状態機械→状態図 |
| モデルとコード、どっちが正しい? | コード。モデルが合わせに行く |
| 意図が分からない | 推測をモデルに書かず、散文で「不明」と残す |

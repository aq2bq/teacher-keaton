# 手法: リバースエンジニアリングから照合まで

SKILL.md が「何を実行するか」の手順書であるのに対し、この文書は
「**どう判断するか**」を掘り下げる。実コードから形式モデルを逆抽出する際の
勘所と、各フェーズの考え方を記す。

## 全体の流れ

```
0. 明確化    良い質問で対象を絞り、理解計画を合意する   (スコープ合意)
1. 調査      コードを読み、概念・状態・遷移・不変条件・関係を見立てる
2. 構造      CUE でスキーマ・語彙・関係を書く        (cue vet)
3. 振る舞い  Quint で状態・遷移・不変条件を書く      (quint typecheck/test/verify)
4. 投影      projection.cue で状態差分の意味づけを書く
5. 整合      check-consistency で CUE↔Quint の語彙整合を検査
6. 照合      explain/project でビューを出し、現実と突き合わせる
   ├─ コードから正しいモデルが一意に決まる → 2〜4 に戻って直す
   └─ コードだけでは意味が決まらない → keaton/TODO.md に根拠を残して人間の判断を求める
```

## 0. 明確化: 理解計画を合意する

形式化は高コストなので、**着手前に対象を絞る**。このフェーズを飛ばすと、
「どこまで・どの深さで・何のために」がLLMの推測になり、期待と異なる成果物に
時間とクレジットを浪費する。要求工学でいうスコープ合意に相当する。

### なぜこの手法で特に重要か

「健全だが完全ではない」が原則なので、「どこまで形式化するか」を必ず誰かが
選ばなければならない。その選択をユーザーの目的で駆動するのがこのフェーズ。
対象を絞る一文が、着手後の膨大な手戻りを防ぐ。

### 5軸の質問

| 軸 | 質問 | 決まること | 例 |
|---|---|---|---|
| **目的** | 何のために理解したいか | 成果物の形 | オンボーディング→`explain`全部入り / デバッグ→特定シナリオの`project` |
| **範囲** | どこからどこまで | モデル化する境界 | 「タスクの状態管理のみ。認証・CLI解析は対象外」 |
| **深さ** | 構造だけか、振る舞い込みか、不変条件までか | CUEだけかQuintまでか | 概要だけ→CUEのみ / 挙動も→Quintまで |
| **焦点** | 振る舞いの何を重視するか | Quintモデルの中心 | 「状態遷移」/「特定の制約」/「データの流れ」 |
| **照合基準** | 何が「正しく理解できた」証拠か | 収束の判定基準 | 「既知の挙動と一致するか」/「実際の出力と照合」 |

### 理解計画の雛形

```
【理解計画】
- 目的: <...>
- 範囲: <...>
- 深さ: <構造のみ | 振る舞い込み | 不変条件まで>
- 成果物: <explain | glossary | 概念マップ | project>
- 照合: <...>
→ この計画で進めてよいですか?
```

この計画が「**できた**」の定義になる。実行中はこれを基準に判断し、
範囲変更が必要になったら勝手に広げず再提示して再確認する。

### 過剰質問にしないための歯止め

- 5軸を**1回の構造化質問**で尋ね、往復を増やさない
- 自明な軸は省略してよい(「このモジュールの概要を見せて」なら目的・範囲が明白)
- 答えられない軸は**推奨の既定を提案して確認**する形にする
  (理解しようとしている相手に全部答えさせるのは本末転倒)
- 「分からない」は有効な入力。その場合はまず浅い概観(用語表+概念マップ)を出し、
  そこから絞る(**段階的な深掘り**)。一度に全部を形式化しようとしない

### 段階的な深掘りの例

```
概要(用語表+概念マップ) → 全体像を把握
   ↓ ユーザーが「状態の動きが知りたい」
振る舞い込み(状態・遷移) → シーケンス/状態図
   ↓ ユーザーが「この制約が本当に守られるか検証したい」
不変条件まで形式化 → quint verify
```

各段で成果物を出して照合し、必要に応じて次へ深掘りする。これで、
最初から全量を形式化するリスクを避けられる。

## 1. 調査: 何を探すか

コードを読んで、次を**書き出しながら**見立てる。頭の中だけでやらない。

| 探すもの | 問い | 例(todo-cli) |
|---|---|---|
| 概念/エンティティ | 名詞は何か。属性は何か | Task(id, title, status, createdAt, completedAt) |
| 状態 | エンティティが取りうる離散状態は何か | backlog / active / done |
| 遷移 | 状態を変える操作は何か。前提条件(ガード)は何か | start: backlog→active |
| 不変条件 | 常に成り立つべきことは何か | idは再利用しない; completedAtはdoneのみ |
| 関係 | 概念同士はどう繋がるか | (状態機械なら状態間の遷移自体が関係) |
| 測度 | 数値は何を測るか。範囲・**極性**・閾値・超過時の意味は何か | (数値尺度を持つシステムのみ) |

### 観測事実と意図の区別

- **観測事実**: コードが現にやっていること。`start` は `backlog` 以外を拒否する、等。
  これはモデルに**そのまま**書く。
- **意図の推測**: なぜそうしているか。コメントや命名から推む。これは**散文**として
  残し、モデルには含めない(含めると願望が混ざる)。

モデルに書くのは観測事実のみ。意図を形式化すると「コードに無い振る舞い」を
モデルが主張し始め、照合の基準が壊れる。

### 値と、値の意味を分ける

数値を読むときは、**「コードがどの値を返すか」**と**「その値がどの状態を意味するか」**
を別々に確認する。前者は追跡すれば必ず分かるが、後者は分からないことがある。
名前で埋めると、確認できていないことが確認済みに見えてしまう。

とくに**極性**(値が大きくなるほど良い状態か、悪い状態か)は名前から推定できない。
「品質」「満足度」のように肯定的な名前で、実際には「悪さ」「気になる程度」
「困りごとの強さ」を測っていることがある。極性の根拠になるのは、閾値を超えた
ときの分岐先、警告の文言、ソート順、色分け、集計での `min`/`max` の取り方など、
**コードが値をどう扱っているか**である。どれも観測できなければ
`polarity: "unresolved"` として未解決の食い違いへ回し、報告では未確認事項として残す。

## 2. 構造(CUE): どこまで書くか

- **スキーマ**: コードが読込時に行っている検証を写し取る。`persistence` 層が
  「重複IDを拒否」「doneならcompletedAt必須」を検査しているなら、それもスキーマに書く。
  コードの検証ロジックは「構造の不変条件」の宝庫である。
- **語彙**: 各概念に `id`(安定識別子)・`preferredName`(表示名)・`definition`(定義)。
  表示名とidentityを分離するのが肝。名前が変わってもidは変わらない。
- **関係**: 概念間の繋がりを `relations` で明示。自然言語に埋めない。
- **測度**: 数値項目は範囲だけでは意味が決まらない。範囲・極性・閾値・超過時の意味を
  一組で `measures.cue` に宣言し、比較の向きは極性から導出する
  (`>=` と `<=` を人が書き分ける箇所を作らない)。詳細は `conventions.md`。

`cue vet -c` で構造を検証する。ここで「語彙の一意性」や「参照整合性」を
構造的に強制できるのがCUEの強みである。実行は `tools/vet` ラッパーを使う
(CUE v0.17.1 では `cue vet -c <相対パス>` がimport path扱いで失敗するため)。

## 3. 振る舞い(Quint): どこまで書くか

- **状態変数**: システムの本質的な状態だけを `var` で。細部(個々のタスクのtitle等)は
  抽象化してよい。振る舞いモデルの関心は「何がどう変わりうるか」。
- **遷移**: 1操作=1アクション。ガード(前提条件)を明示する。ガードこそが
  「許される振る舞い」の定義である。
- **不変条件**: 「常に成り立つこと」を `val` で。例:「idは再利用されない」
  「勝利と敗北は排他」。不変条件はモデルの主張であり、`quint verify` で全経路を検証できる。
- **シナリオテスト**: `run ...Test` で代表的な筋を書く。宣言(期待する振る舞い)になる。
- **測度を扱う場合**: 閾値との比較は `gen-quint-constants` が極性から生成した
  `<閾値>IsWorseSide` / `<閾値>IsBetterSide` を使い、生の `v >= 3` を書かない。
  テストは動作(閾値の前後で結果が変わる)と意味(極性と閾値の解釈が仕様と一致する)を
  分け、意味の側は頂層 `val` の不変条件として書く。

### 宣言が荷重部材か確認する(ミューテーション)

不変条件と同じ問いを、測度の極性にも当てる。**宣言した極性を反転させたとき、
`vet` かQuintのテストが必ず落ちること**を確かめる。落ちないなら、その極性は
モデルのどこにも効いておらず、宣言が飾りになっている。

### 不変条件が空虚でないか確認する

不変条件を意図的に外して `quint verify` にかけ、違反トレースが出るか確かめると、
その不変条件が**実際に制約として機能している**ことを証明できる(ミューテーションテスト)。
常に自明に真の不変条件は書く価値が薄い。

## 4. 投影(projection.cue): 意味づけの宣言

「状態差分が何を意味するか」を宣言する。ここが**システム固有の解釈**の置き場所。

- ナラティブ(参加者間の相互作用)なら `message`(シーケンス図)。
- 状態機械(レコードの状態変化)なら `transition`(状態遷移図)。

差分述語(`setGains` / `move` / `intDecreases` / `boolBecomes` 等)のANDで
イベントを検出し、`bind` で捕まえた値を `from`/`to` で `$<bind>` として参照する。
詳しくは `conventions.md` と `examples/*/spec/projection.cue`。

## 5. 整合: CUE↔Quint の語彙を揃える

`check-consistency` は次を検査する:
- Quintの文字列リテラルがCUEの既知idか(未知idは失敗)
- Quintに日本語/生リテラルが漏れていないか
- `constants.qnt` がCUEと一致しているか(鮮度)

これにより「QuintはCUEの語彙を参照する」という約束が機械的に保たれる。

## 6. 照合: メンタルモデルを築く

`explain` で全部入り解説書を出し、人間と現実(実コードの実際の挙動)に突き合わせる。

- **学習モード**: 初めてのシステムで `explain` を叩き、用語→構造→振る舞いの順に
  メンタルモデルを築く。
- **分析モード**: 特定のシナリオ(`--test`)やcounterexample(`--trace`)を投影し、
  「なぜこうなるか」を調べる。

ビューは完成品ではなく、照合のための**提案**である。人間の役目は正しい理解を
ゼロから生成することではなく、この提案を判定することなので、最終報告は必ず
**明示的に判定を依頼する**: 判定依頼の列挙(語彙・境界・不変条件・関係・測度の極性)、
フェーズ0で合意した照合基準との突合、反応のしかたの案内(「Xは実はY」の形で
指摘してもらう)を含める。依頼を省略すると、ビューは完成品として鵜呑みにされ、
照合が起きない。

食い違いは発見である。
ただし、検証を通すこと自体を目的にして語彙や制約を補ってはいけない。
CUEとQuintは、入力した前提に対する整合性を検査するのであり、前提の意味が正しいことを
保証するわけではない。結果に記載された探索深度までQuintで反証が見つからなくても、教育・記録・
遵守などが現場で実施されているかは別途確認が必要であり、運用の適合証明として扱わない。

### 食い違いを誰が解決するか

検証失敗、Quintの反証(counterexample)、または実コードとの食い違いを見つけたら、
実コードと検証結果を追加調査する。
その結果により、次のように処理を分ける。

| 調査結果 | 処理 |
|---|---|
| 実コードから正しいモデルが一意に決まる | エージェントがモデルを修正し、関連する検証と投影をやり直す |
| 合意済みの範囲内を追加調査すれば決められる | 根拠を追加調査してから再判定する |
| 調査範囲を広げなければ決められない | 理解計画を再提示し、ユーザーの承認を得る |
| 追加調査後も一つの語彙または論理構造へ収束しない | 推測で解消せず、対象プロジェクトの `keaton/TODO.md` へ記録する |
| 数値の極性が実コードから決まらない | 名前から向きを決めず `polarity: "unresolved"` とし、依存する判定・閾値・図を保留して `TODO.md` へ記録する |

最後の行に該当する食い違いを**未解決の食い違い**と呼ぶ。
同じ `preferredName` が複数の安定idを指す場合も、実コードに既存の区別がなければ
表示名を発明せず、未解決の食い違いとして扱う。

### 未解決の食い違いが残る範囲

未解決の食い違いに依存するモデル要素とビューは、正しい前提を選べないため確定しない。
依存しない範囲は「健全だが完全ではない」という原則に従って検証し、成果物として出してよい。
中心概念が未解決なら、それに依存する後続フェーズも止める。

`TODO.md`には、両立しない観測事実と出典、検証失敗または反証、両立しない理由、
保留したモデルとビュー、ユーザーに求める判断を記録する。
最終報告では `TODO.md` のパス、レベル2見出しを数えた未解決項目数、保留した範囲を
明示し、対処を依頼する。

ユーザーの判断後はモデルを更新し、影響範囲のCUE検証、Quint検証、語彙整合検査、投影を
やり直す。
解決した項目は `TODO.md` から削除し、未解決項目がなくなったらファイル自体を削除する。

## 判断に迷ったら

| 迷い | 指針 |
|---|---|
| どこまで対象にすべき? | 推測せず**理解計画**(フェーズ0)に立ち返り、ユーザーと合意する |
| これ形式化するべき? | 機械検査して価値があるか。なければ散文で |
| どこまで詳細に? | 振る舞いの本質だけ。細部は抽象化 |
| どのビュー? | システムの構造に合うもの。ナラティブ→シーケンス、状態機械→状態図 |
| モデルとコード、どっちが正しい? | コード。モデルが合わせに行く |
| 意図が分からない | 推測をモデルに書かず、散文で「不明」と残す |
| 数値の向きが分からない | 名前から決めない。`unresolved` として `TODO.md` へ回す |
| コードだけでは語彙か論理構造が決まらない | 根拠を `TODO.md` に残し、依存する範囲を保留してユーザーに判断を求める |

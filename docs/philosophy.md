# 哲学: セマンティック・リバースエンジニアリング

この文書は teacher-keaton の設計思想を記す。セッションの経緯を知らなくても
意図が伝わるように、**なぜこの手法に辿り着いたか**を書く。

## 出発点の課題

AIエージェントによる開発では、コード生成能力そのものより、**人間とAIの間の認識のずれ**
が問題になる。ずれるのは:

- ドメインの概念・用語の意味
- コンポーネントの責務・境界・依存
- 状態遷移・不変条件・禁止される振る舞い
- 既存実装が暗黙に抱えている仕様

自然言語のドキュメントだけでは、これらが曖昧になり、実装との乖離を機械的に検出できない。
一方で、重厚な要求管理(DOORS等)やMBSE、オントロジー構築に振りたいわけでもない。

## 仮説

> ソフトウェアの設計・仕様を、**Gitで管理可能な、機械可読かつ検査可能な中間表現
> (Specification IR)** として持つことで、AIエージェントによる開発を安定させられる。

普段の開発の道具立て(plain text / Git / diff / PR / CI / CLI / parser)の延長で実現する。

## 目指すもの: セマンティックインターフェース

最終目的は、単なるドキュメント生成ではない。

> **実コードを事実源としてリバースエンジニアリングした形式モデルを介し、人間が
> 目的別にシステムの意味を理解するためのセマンティックインターフェース**

つまり「コード → 形式モデル → 複数のビュー → 人間の理解」という経路を、道具として
成立させること。ビューは**目的別**(学習のため、分析のため、レビューのため)に選べる。

## 手法の全体像

```
実コード(事実源)
   |  リバースエンジニアリング
   v
形式モデル(Specification IR)
   |-- CUE   : 構造・語彙・関係   (静的に保証できること)
   |-- Quint : 状態・遷移・不変条件(時間とともに変化する振る舞い)
   |  投影(projection)
   v
ビュー: 用語表 / 概念マップ / シーケンス図 / 状態遷移図
   |  照合(reconcile)
   v
人間のメンタルモデル  ← 食い違いを見つけてはモデルを直し、再投影する
```

### なぜ2層か

- **CUE** は「このデータ/構造は妥当か」を検査する層。概念・語彙・関係・スキーマを
  宣言し、unification で一意性や参照整合性を**構造的に強制**できる。
- **Quint** は「この振る舞いは許されるか」を検査する層。状態遷移・不変条件を
  実行可能な仕様として書き、シミュレーション/モデル検査で検証できる。

この分担は「静的に保証できること」と「時間とともに変化するもの」の自然な境界に対応する。

### なぜ投影か

メンタルモデルは、**複数の整合したビューを現実と突き合わせる**ことで築かれる。
用語表は「何が存在するか」、概念マップは「どう繋がっているか」、シーケンス/状態図は
「時間に沿って何が起きるか」を答える。すべて同じCUE語彙とQuint振る舞いから派生するので、
ビュー間で用語と構造が**構造的に一致する**。この「一貫性で通底している」ことが、
個々の図の正しさより重要である。

### なぜ照合か

図は鑑賞物ではなく**照合面**である。投影を人間の実像(あるいは実コードの実際の挙動)と
突き合わせ、食い違いを見つける。食い違いを見つけた後は、根拠によって扱いを分ける:

- モデルが間違っている → モデルを直す
- 人間のメンタルモデルが不完全だった → ビューが何かを教えた
- 実コードの観測事実が一つの意味に収束しない → 推測で解消せず、人間の判断を求める

このループが「理解」を前進させる。

CUEとQuintが検査するのは、モデルへ入力した語彙と論理構造に対する整合性である。
入力した前提が実コードから導けることまでは保証しない。
エージェントが検証を通すために表示名や制約を発明すると、推測した前提が形式手法によって
補強され、誤ったメンタルモデルを信頼しやすくなる。

そこで、追加調査後も実コードだけでは一つの語彙または論理構造へ収束しない食い違いを
**未解決の食い違い**と呼ぶ。
未解決の食い違いは形式モデルへ推測で入れず、観測事実、検証失敗、反証(counterexample)、
影響範囲を `keaton/TODO.md` に残して人間の判断へ渡す。
この記録により、検証済みの語彙と論理構造、その反証を、エージェントの説明や推測から
区別できる。

## 原則

1. **健全だが完全ではない(sound but not complete)**。機械検査する価値のあるものだけ
   形式化する。根拠・トレードオフ・設計意図は自然言語のままでよい。
2. **事実源は実コード**。形式モデルはコードから逆抽出する。コードに無い振る舞いを
   モデルに足したら、それは願望であり発見すべき差異である。
3. **DSL作りを目的化しない**。既存形式(CUE/Quint)で十分ならそれを使う。
4. **オントロジー構築に振らない**。欲しいのはソフトウェア仕様であり、知識体系ではない。
5. **カジュアルな道具立て**。plain text / Git / CLI / CI の延長で、特別なGUIや
   専用環境を要しない。
6. **汎用コアとシステム固有の解釈を分離する**。ツールは汎用の機械に徹し、
   「状態差分をどう意味づけるか」は各システムの `projection.cue` が宣言する。

## 避けるべきこと(反面教師)

- **ツールにドメインをハードコードする**: かつてシーケンス図ツールが桃太郎の状態変数と
  語彙を焼き込み、他システムに使えなくなった。ドメイン解釈は `projection.cue` へ
  切り出した。これが本プロジェクトの最重要の設計判断である。
- **全ビューを強制する**: ナラティブに状態図を、状態機械にシーケンス図を無理に
  出さない。適応型で、合うビューだけ出す。
- **形式化の網羅性を競う**: 全部を形式化しようとすると破綻する。価値のある部分に絞る。
